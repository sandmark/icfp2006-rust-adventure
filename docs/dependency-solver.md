> **現在の課題**: adventure の複数の部屋にまたがる依存関係を解き、`uploader` /
> `downloader` を組み上げる手順を、VM とやり取りせず机上で計算するソルバを設計する。
> 本書はその設計途中の記録で、完成仕様ではない。
> 記述は **観測された事実** と **仮説（検討中）** の二層に分ける。
>
> データ実体: `local/chicago-rooms.xml` — 今行ける13部屋を `switch xml` → `look` + 12回の `go` で
> 調べた XML。以下の観測は、この1回の走査に基づく。
>
> 参考データ実体: `local/tutorial.xml` - 初期エリア2部屋を `look`, `go` で調べた XML。
> 手動で経路探索できる規模であり、 `keypad` を完成させるのがゴールだった。

## 課題とねらい

ICFP2006 UMIX 内のテキストアドベンチャー（作者 howie）の皮を被った依存関係パズル。
壊れたアイテムを `combine` で修理・合成しながら進み、`uploader` / `downloader` を
組むのが節目になる。ねらいは **「行ける全部屋を最初に一度調べ、あとは机上で全手順を
計算して出力する」ソルバ** を作ること。

シェル本体の構成は CLAUDE.md を参照。本書はソルバ設計に固有の観測と仮説だけを扱う。

## 観測された事実

`local/chicago-rooms.xml`（13部屋を1回走査）とプレイ中の観測に基づく。ここでの「プレイ」は
**1回の起動からクリア／終了までの一続き** を指す。

### 速度
- `go` / `look` は部屋のアイテム数に比例して遅い（数秒〜十数秒）。`show`（手持ちは最大6個）は速い。

### アイテムの同一性 = (`name`, `adjective`)
- **同一性は (`name`, `adjective`) の組で決まる**。同じ `name` でも `adjective` が違えば別のアイテム。
  この一つ一つを **バリアント** と呼ぶ。
- 観測例: `X-1623-GTO` は `adjective` 違いで9種、`T-0010-BQH` は7種、`MOSFET` は3種（`local/chicago-rooms.xml`）。
- 依存（欠品）は XML 上 **`name` だけ** で指定され、`adjective` を持たない（`docs/xml.md`）。
  そのため「その依存がどのバリアントを指すか」は XML だけでは決まらない（→ 仮説「バリアントの割り当て」）。

### 状態（pristine / broken）
- アイテムの状態は **pristine**（欠品なし）か **broken**（欠品あり）。broken は欠品を `combine` で挿して修理する。
- **broken でも無用とは限らない**——broken のまま、別のアイテムの材料（依存）として使える場合がある（観測）。
- 状態が決めるのは **そのアイテム自身に修理（`combine`）が要るか** だけで、他のアイテムの材料として使えるかどうかとは無関係。

### 手持ち（インベントリ）
- **6枠まで**。`combine` する2つは **両方とも手持ちに要る**（地面の物とはその場で合成できない → 両方とも先に `take` する）。
- `combine` は片方を消費する（手持ちは実質 −1、修理済みの片方が残る）。`incinerate`（inc）は破壊（−1）。

### 地面（スタック）
- 地面は後入れ先出しで、`take` で取れるのは **一番上だけ**。下の物を出すには、上の物を先に `take` する（その分だけ手持ちの枠を使う）。
- `incinerate` は **手持ちのアイテムにしか使えない**。地面の物には使えず、地面の一番上を除ける手段は `take` だけ（確定）。
- `examine` / `look` は、下に埋もれた物も含めて **山全体を見せる**（取れるのは一番上だけだが、中身は全部読める）。
- 地面へ戻す（`drop`）ができるかは未確認。

### 地形
- **現在の攻略段階（シカゴシティ）** は碁盤の目状（XX番街 × YY通り）に並んだ ~4×4 の13部屋。
  地図の端はつながっておらず、反対側へ回り込めない。この地形はこの段階に固有。

## 仮説（検討中・要検証）

以下は観測から導いた作業仮説で、確定していない。実装は「仮説である」と分かった上で進める。

- **プレイ間で変わらないか**: 1回のプレイの中では `name`・`adjective`・依存は変わらないように見える。
  ただしプレイをまたいで（再起動ややり直しの後で）同じかは未検証で、注意が要る。
- **必要な部品はシカゴシティ内に揃っている**: 今行ける範囲が13部屋より外へ広がらないのは観測。
  ここから、必要な部品は今の到達範囲の中に揃っていると考えている。
- **依存の再帰には底がある（本命）**: あるアイテムの依存をたどっていくと、最終的に
  **それ自身は何も必要としないアイテム（依存関係の葉）** に行き着くと考えている。これが成り立てば、
  手順を組み立てる計算は必ず有限で止まる。底かどうかは pristine か broken かとは無関係で、
  本質は「そのアイテムが何かを必要とするか」「他から必要とされるか」だけ。

## 検討中の設計

### 方針: 一度調べて、あとは机上で解く

- **やり方** — 行ける全部屋を最初に一度だけ調べ、その結果を **あとは変えない入力** として、
  そこから全手順を計算して出力する。
- **なぜ** — ねらいが「VM とやり取りせず机上で全手順を出す」である以上、
  **常駐同期方式**——プログラムを動かし続け、`combine` などで VM 側の状態が変わるたびに
  手元の記録も書き換えて追随させる方式——は、VM と往復し続ける点でねらいと論理的に衝突する。
  加えて、VM 側と手元で状態を二重に持てば食い違いの元になる。だから最初の1回の調査結果を
  固定した入力として扱い、以後は VM に問い合わせない。13部屋を毎回問い合わせるのは遅すぎる、
  という速度の観測もこれを後押しする。
- **もしずれたら** — 出力した手順を実行して想定と食い違ったときは、全部屋を **調べ直して**
  計算をやり直す（このやり直しも前の状態を引きずらない）。

### アルゴリズム: 依存の解決と手順の組み立て

- 依存関係をたどるときは、各アイテムを (`name`, `adjective`) で区別する。
- **バリアントの割り当て（仮説・未実装）**: 依存要求は `name` だけだが、
  「6枠の空きで作れるもの」＋「地面から取れる数」＋「一番深い部品から順に組み上げる」を
  合わせれば、どのバリアントを指すかが一意に定まると考えている。
  - **なぜ総当たりでなく葉から順に組み上げるか**: 割り当てが一意なら選択肢がなく、
    探索せずに決定的に解ける。この選択は **一意性の仮説に全面的に依存する**——
    仮説が崩れれば総当たり探索に戻す。
- **6枠に収まるか（解けるか）** — 組み立てを「6枠の作業台で順番に作る」問題として見る。
  - `combine` は手持ちの2つを取り、片方を消費して、修理済みの片方が残る（置き場は増えない）。
  - `drop` ができないなら、作りかけを一時的に地面へ逃がして枠を空けられない（`drop` 可否は未確認）。
  - **同時にいちばん多くの枠を使う部分から先に作れば、同時に抱える枠数の最大が下がる**。
    この最大が6以下なら6枠に収まり、解ける。
- 同時に満たすべき制約: **各バリアントの在庫は到達範囲にある分だけ（無限には湧かない）** /
  **地面は後入れ先出しで取れる順番が決まっている** / **`combine` は2つとも手持ちに要る**。
  完全なソルバはこれらを同時に満たす必要がある。
