# 依存解決ソルバ 設計仕様

**日付**: 2026-07-04
**状態**: 設計方針は確定・実装前。詳細アルゴリズムと一部のゲーム機構は未確定（§10「未解決の疑問」参照）。
**対象**: ICFP2006 UMIX 内のテキストアドベンチャーを、依存関係パズルとして机上で解くソルバ

> このドキュメントは単独で読んで理解できるよう完結させている。関連文書（背景の観測ノート・
> シェル本体の構成・XML 応答形式）は §11 参考リンクにまとめた。本書だけで設計は追える。

## 1. ねらい

このアドベンチャーは、壊れたアイテムを `combine` で修理・合成しながら進む依存関係パズル。
ねらいは、**到達できる全部屋を最初に一度だけ調べ、その結果を固定入力として、あとは VM と
やり取りせず机上で全手順を計算して出力するソルバ**を作ること。

ソルバは3つのコマンドから成る:

- **walk** — 到達できる全部屋を調べ、世界のスナップショットをメモリに作る。
- **solve `<item>`** — `<item>` を pristine にする手順列を、6枠制約を守って計算・表示する（VM には触れない）。
- **make `<item>`** — solve が出した手順列を実際に UM へ流し込む。

「手順列」は `take` / `combine` / `incinerate` / `go` を一列に並べたもの（§7 で make がそのまま流す）。
ソルバのゴールは「指定した `<item>` が pristine になること」で、ゲーム全体の進行・クリア判定は扱わない
（それは層1＝プレイヤーの領分、§6・§9）。walk / solve / make の起動形態と状態の受け渡しは §10 参照。

## 2. ドメインモデル（前提知識）

（この節だけで、combine パズルの規則が分かる。）

### 用語
- **item / バリアント** — アイテムの同一性の単位。同一性は (`name`, `adjective`) で決まり、
  同じ `name` でも `adjective` が違えば別バリアント。
- **condition（状態）** — バリアントの状態。本書は `pristine`（欠品なし）と `broken`（欠品あり）の
  2値でモデル化する。
- **slot（スロット）** — `broken` なアイテムに空いた穴。1つの穴は「そこに埋めるべき部品の要求」を表す。
- **kind** — スロットが要求する部品の種別。`(name, condition)` の組で表す（`adjective` を含めない
  ＝バリアントは指定しない）。

### アイテムの同一性
- アイテムの同一性は **(`name`, `adjective`) の組**で決まる。同じ `name` でも `adjective`
  が違えば別物で、これを**バリアント**と呼ぶ（例: transistor は blue "PNP-complete" と
  red "NPN-complete" が別バリアント）。

NOTE: (a) `adjective` の無いアイテムの同一性が `name` だけで決まるのか、(b) 例の
「blue "PNP-complete"」でどちらが `adjective` に当たるのか、は本書では未定義。実データで確認する。

### 状態（condition）
- アイテムの状態は **pristine**（欠品なし）か **broken**（欠品あり）。
- broken は「**欠けている kind のリスト**」と「**それらを埋めた後の状態**」を持つ。
  後者はさらに broken でありうる（多段の broken）。多段のとき、外側の段（今スロットが空いている段）の
  欠品を**外欠**、それを埋めた後に現れる内側の段の欠品を**内欠**と呼ぶ
  （§8 の A-1920-IXB「二重 broken」＝ 外欠1段＋内欠1段）。
- **欠けている kind は `name` と `condition` を持つが、`adjective` は持たない**。
  つまりスロットは「名前 N で状態 C のアイテム」を要求し、バリアントは指定しない。
  → **スロットの `condition` が、そこに挿すべき部品の目標状態を決める**（後述の罠の核心）。

### combine と inventory
- `combine A B` は、A の欠けたスロットに合う B を挿し、**B を消費**して A の状態を1段進める
  （スロットが埋まる。まだ欠品が残れば A は broken のまま）。
- **A も B も両方インベントリに要る**（地面の物とはその場で合成できない）。
- インベントリは **6枠**。枠の増減は `take` が +1、`combine` が実質 −1（挿した B が消える）、
  `incinerate` が −1、`go`（移動）は ±0。

NOTE: A に同一 (name, condition) のスロットが複数ある場合、`combine A B` がどれを埋めるか
（選択・順序の規則）は未定義。
NOTE: 6枠が固定か、ゲーム内で変化しうるかは未確認（本書は6固定として扱う）。

### 地面（ground）と移動
- 地面は**後入れ先出し（LIFO）の山**。`take` で取れるのは**一番上だけ**。下の物を出すには
  上を先に `take` する（その分だけ枠を使う）。
- `incinerate` は**インベントリの物にしか使えない**。地面の一番上を除ける手段は `take` のみ。
- `look` / `examine` は山全体（埋もれた物も）を見せるが、取れるのは一番上だけ。
- `drop`（地面へ戻す）の可否は**未確認**（noop の可能性あり）。本設計は drop に依存しない。
- 部屋の移動は `go <方角>` で行う。方角は部屋の `<description>` の地の文にだけ書かれている
  （例: 「A hallway leads north.」）。`go` の応答自体は移動方角を返さない。

## 3. アーキテクチャ / データの流れ

```
walk ─(1回だけ)─▶ Snapshot（不変） ─▶ solve(item, snapshot, state) ─▶ 手順列 ─▶ make ─▶ UM
                                                                    └▶「不可能」
```

- **一度調べて固定する**理由: ねらいが「VM と往復せず机上で解く」である以上、状態が変わる
  たびに VM へ問い合わせる常駐同期方式はこの方針に反し、二重管理の食い違いも生む。
  NOTE: 「毎回問い合わせるのは遅すぎる」という速度面の根拠は実測値を持たない（体感）。定量化は未着手。
- **ずれたら**: 出した手順を実行して想定と食い違ったら、全部屋を**調べ直して**やり直す
  （このやり直しも前の状態を引きずらない）。
  NOTE: 「ずれ」が起きる想定原因、および walk 全体のやり直しではなく差分更新で済ませる案の可否は未検討。

## 4. walk

**責務**: 到達できる全部屋を巡回し、Snapshot を1つ作る。VM への `switch xml` → `look` →
出口ごとの `go` で回る。

**出口の発見（方針 a）**: 各部屋の `<description>` を parse し、`... leads <方角>` の類から
出口の方角を拾って巡回する。隣接は walk 自身の移動から記録できる（`go north` を送って
着いた先が分かるため、隣接辺は自分の移動の副産物として溜まる）。
- 前提: description が出口を必ず列挙している。tutorial では成り立つ。Chicago の言い回しは
  実データ（`local/chicago-rooms.xml`）で確かめてから確定する。

NOTE: walk の巡回アルゴリズムは未確定。少なくとも次が未決 — 巡回方式（DFS/BFS）と frontier・
訪問済み判定・終了条件／部屋の同一性の判定基準（同名部屋の扱い）／逆向きが非対称な場合の
バックトラック手段（全部屋巡回が破綻しうる）／`... leads <方角>` の parse 具体（言い回し一覧・
up/down/in/out 等）／`go` 失敗時のエラー処理／walk が read-only か（take するか）／
walk 終了後の現在地を solve の初期 `current_room` へどう渡すか。

## 5. データ構造

Snapshot は次を持つ:

- **部屋の有向グラフ**: ノード＝部屋。辺＝`go` に渡す**方角トークン**でラベル付けした有向辺
  （`RoomWithADoor --north--> JunkRoom` と逆向き `--south-->`）。solve の経路探索（go 列の
  生成）に使う。方角は逆向きが必ずしも対称とは限らないので、辺は向きごとに明示的に持つ。
- **各部屋の LIFO スタック**: その部屋の地面の山を、上から順に並べた item 列。段（深さ）が
  「掘るコスト（何個 take するか）」に対応する。
- **item → (部屋, 段) 索引**: 「この item はどこの山の何段目か」を引くため。

各 item は §2 の condition（pristine / broken の多段構造）を自身に持つ。solve が必要とする
依存木は、対象 item のこの broken 構造から導く（Snapshot に別個の依存木は持たない）。

NOTE: item 索引のキーは同一性 (name, adjective)。同一バリアントが複数の山・段に重複する場合の
表現（値を (部屋, 段) の集合にするか）は未確定。

solve が引きたい2つの問い——「item X はどこの何段目か」「部屋 A から B へどう行くか」——に
両方これで答えられる。Snapshot は生成後**不変**として扱う。

## 6. solve

### シグネチャ

```
solve(item, snapshot, state) -> 手順列 | 不可能
  state = { inventory: 手持ちのアイテム集合, current_room: 現在地 }
```

- **item** … pristine にしたい対象。
- **snapshot** … walk が作った不変の世界。
- **state** … 現在のインベントリと現在地。go を出すには居場所が要り、6枠判定には手持ちが要る。

NOTE: `item` 引数が同一性 (name, adjective) 全体か `name` だけか、また `state.inventory` が
集合か多重集合か（同一バリアントの重複、例: transistor 2個の表現）は未確定。

### セマンティクス

solve の責務は**「item を pristine にする手順列を、6枠を守って出す」ことだけ**。ゲームとして
詰むか否かは責務外（例: `solve radio` は radio を pristine にする手順を出す。それが詰みルート
でも solve は関知しない）。

**スロット条件で止まる再帰（罠を踏まない核心）**:
- あるアイテムを pristine にするには、欠けた各スロットを埋める部品を用意して `combine` する。
- **各スロットの目標状態は、そのスロットの `condition` が決める**。pristine を要求するスロット
  なら部品を pristine まで作り、broken を要求するスロットなら**その broken 状態で止める**。
- トップレベルの `item` だけが「pristine」を目標に取り、サブ部品の目標はスロット由来。
  これにより `solve keypad` は radio を「broken・欠 antenna」で止め、**完成させない**
  （下記テストケース参照）。もしサブ部品を一律 pristine にすると radio を完成させすぎて詰む——
  それは一意に決まる依存を解けていないので**バグ**。
- 本設計は、combine が誤状態の部品を拒否／消費のどちらで扱うかには依存しない——solve が常に
  正しい状態の部品を用意するため（combine 側の挙動が未確認である件は §10）。

**2層のスケジューリング**:
- solve は依存木を解く関数ではなく、**LIFO の山の上で `take`/`combine`/`incinerate`/`go` を
  一本の列に並べるスケジューラ**。木は「何が要るか」しか答えず、順序も枠数も移動も持たない。
  → **6枠に収まるかは、木を見ても分からず、手順列を実際に組んで初めて判定できる。**

NOTE: solve の中核アルゴリズム（探索か貪欲か、バックトラックの有無、状態空間の定義）は本書では
未確定。「手順列を実際に組んで判定する」と述べるが、その組み方自体は実装時に決める。
- 「何から作るか」は2層に分かれる:
  - **層1（ターゲット間）** — uploader / downloader / MOSFET 等、どのゴールをどの順で作り、
    完成品を抱えたまま次へ進むか。これは**プレイヤーの判断**で、solve の外。
    「uploader/downloader を持ったまま MOSFET を作れるか？」の答えは、solve に現在の
    `state.inventory` を渡して「不可能」が返るかで分かる。
  - **層2（ターゲット内）** — 1回の solve の中で、どのサブ部品から作れば「**同時に抱える
    枠数の最大 ≤ 6**」に収まるか。これは solve の中身。最も多く枠を使う部分から先に作れば
    同時に抱える枠数の最大が下がり、この最大が6以下なら収まって解ける。

NOTE: 「最も多く枠を使う部分から先に作れば同時に抱える最大が下がる」という貪欲則が常に最小 peak を
与えるかは未証明（反例の非存在も未確認）。各部分木の peak 枠コストの見積もり式も未定義。

**在庫ゴミの扱い（副産物）**:
- どこからも必要とされないアイテム（例: tutorial の spring, red pill）は、「solve の手順に
  出てこない」ことでしか判定できない。この判定を別パスにせず、**solve が必要な item に
  たどり着くために山を掘る過程で、邪魔な物を `take` → `incinerate` する**副産物として出力する。
- 山から退けた item の処分は3択:「後で使うので**持ち続ける**（枠を消費）／要らないので
  **incinerate**／drop（可否不明・依存しない、§2）」。どれを選ぶかが6枠に収まるかを左右する。

NOTE: 3択のどれを選ぶかの決定ロジック（基準）は未定義。

**移動**: 部品や対象が別部屋にあれば、solve は経路を探索して `go <方角>` 列を手順に含める
（将来 `solve uploader` が部屋移動を出力する場合の一般形）。

NOTE: 経路探索アルゴリズム、および複数部屋を往復する場合の訪問順の最適化は未指定。

**不可能の報告**: どう並べても層2が6枠に収まらなければ、手順列の代わりに「不可能」を返す。

NOTE: 「不可能」の要因として本書が挙げるのは層2の枠オーバーのみ。部品の供給不足・必要 item が
山に無い・目的部屋が到達不能などの他要因、および「どう並べても6枠に収まらない」ことを網羅的に
確認する探索の完全性は未整理。

## 7. make

**責務**: solve が出した手順列を、そのまま UM へ流し込む（`take`/`combine`/`incinerate`/`go`）。

solve と make を分けるのは、**計算（プレビュー）と実行**を分離するため。solve の出力を人が
確認してから make で実行できる。

NOTE: make が UM 応答を parse して想定と照合し、ずれを検知する具体手順（§3 の「ずれたら再 walk」を
起動する判定）は未記述。make 開始時の state（現在地・手持ち）を何を根拠に信じるかも未整理。

## 8. テストケース: チュートリアル（Junk Room）

初期エリアの2部屋。手動で経路探索できる規模で、`keypad` を pristine にするのがゴール。
`local/tutorial.xml` が実データ（fixture として使う）。

**Junk Room の山**（上→下）: bolt, spring, button, processor〈欠 cache〉, red pill,
radio〈欠 transistor, antenna〉, cache, transistor(blue), antenna, screw,
motherboard〈欠 A-1920-IXB, screw〉, A-1920-IXB〈二重 broken〉, transistor(red),
**keypad**〈欠 motherboard, button〉, trash

（開始部屋は "Room With a Door"（pamphlet / manifesto のみ）。keypad と部品は全部 Junk Room にある。）

**keypad の依存木**:

```
keypad             欠: motherboard, button
├─ motherboard     欠: A-1920-IXB, screw
│  ├─ A-1920-IXB   外欠: radio〈broken:欠 antenna〉, processor, bolt / 内欠: transistor
│  │  ├─ radio     目標=broken・欠 antenna → 山の radio(欠 transistor,antenna)に
│  │  │            transistor だけ挿す（antenna は挿さない）
│  │  ├─ processor 目標=pristine → 山の processor(欠 cache)に cache を挿す
│  │  ├─ bolt      pristine（そのまま）
│  │  └─ transistor pristine（そのまま）
│  └─ screw        pristine（そのまま）
└─ button          pristine（そのまま）
```

transistor の需要=2（radio スロット＋A-1920-IXB 内）、供給=2（blue, red）。どちらの色でも
スロットは受けるので交換可能。

**このテストで押さえられる点**:

| 設計要素 | tutorial でのカバー範囲 |
|---|---|
| 再帰的な依存分解（keypad→…→radio） | ✅ 深く試せる |
| スロット条件で止まる（radio を broken・欠 antenna 止まり） | ✅ 最重要。完成させないことの検証 |
| LIFO 掘り＋6枠＋在庫ゴミの incinerate（spring, red pill が邪魔） | ✅ 試せる |
| solve が go を出す | △ 開始部屋→Junk Room の `go north` 一本のみ |
| バリアント割り当ての一意性 | △ transistor 2個が交換可能で衝突せず、実質テストにならない |
| 層1（複数ターゲット順・完成品を抱えたまま） | ✗ ターゲットは keypad 単体、インベントリは常に空 |

→ 最初の実装範囲は **再帰・スロット条件・LIFO/6枠** の3点（✅）に集中し、△✗ は割り切る。

**テスト規約**: 各 `#[test]` は英語のfn名＋日本語コメント（正常系/異常系の意図）をセットで書く
（`CLAUDE.md` の規約）。`local/tutorial.xml` を fixture として parse し、solve の出力手順列を
検証する。

NOTE: 各テストの期待値（「正しい手順列」）をどう定めるか——出力の同値判定を順序不問にするか、
枠 peak が条件を満たしていればよしとするか——は未定義。radio を「broken・欠 antenna」で止めることを
テストでどう確認するか（手順列に radio への antenna 挿入が現れないことの確認など）も要具体化。

## 9. スコープと先送り

- **バリアント割り当て**（スロットは `name` だけ指定、どのバリアントを充てるか）は、
  「6枠で作れる物＋地面から取れる数＋葉から順に組む」で一意に定まる、というのが作業仮説。
  tutorial では衝突しないため、Chicago で本格的に必要になるまで先送り。仮説が崩れたら
  総当たり探索に切り替える。
  NOTE: 「仮説が崩れた」ことをどう検知するか（何を観測したら総当たりへ切り替えるか）は未定義。
- **層1（ターゲット間の順序）** はプレイヤーの領分。solve は state を受けて可否を返すのみ。
- **drop の可否** は未確認（§2）。退けた物は持ち続けるか incinerate で処分する。

## 10. 未解決の疑問 / エラー処理

設計判断やアルゴリズムが未定の論点は、本文の該当箇所に `NOTE:` で示した（§1 起動形態、
§2 同一性・枠・スロット、§3 速度/ずれ、§4 walk 巡回、§5 索引、§6 solve 中核・貪欲則・経路・
不可能・処分、§7 make 照合、§8 テストの期待値、§9 バリアント割り当ての崩れ検知）。以下は
分類しにくい横断項目とエラー処理方針。

- **呼び出しインターフェースと状態の保持**: walk / solve / make を既存シェルにどう組み込むか
  （サブコマンド／対話中の内部コマンド／別バイナリ）、および walk の Snapshot・solve の手順列を
  プロセスをまたいでどこに保持するか（メモリ常駐／ファイル）は未確定。
- combine が誤状態・誤バリアントの部品をどう扱うか（拒否／消費）は未確認。solve は常に
  正しい状態を用意するので、正常系は影響を受けない。
- 出口 parse（方針 a）は Chicago の言い回しで再検証が要る。
- walk 中の parse 失敗（description から出口が取れない）が Snapshot 構築を止めるのか、
  部分的に続行するのかは未記述。
- solve が「不可能」を返すのは、層2が6枠に収まらないと判明したとき。make はそれを実行しない。
- XML parse 失敗時の扱いは既存シェルの `[PARSE ERROR]` 経路に従う（`CLAUDE.md` 参照）。
