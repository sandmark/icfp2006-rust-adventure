# 編集者の改訂指示書 ―『依存解決ソルバを Rust で書く（初稿）』

> 立場: 初稿本体（`docs/books/dependency-solver.md`）と生徒レビュー（`review/01-student-questions.md`）を、
> 設計仕様（`docs/superpowers/specs/2026-07-04-dependency-solver-design.md`）と実在型（`src/parser.rs`）に
> 照らして裁いた。本文の書き換えは行わない（改訂は教師の役目）。ここに記すのは「取捨選択の判断」と
> 「日本語の健全性チェック」。
>
> 判断軸は3つ ―― (1) 読者理解が進むか、(2) 設計仕様から外れないか、(3) 開示度を壊さないか。
> **開示度の線引き（最重要）**: 骨格・型の形・関数シグネチャ・テストの書き方は開示してよい。
> `solve` の層2スケジューラ（順序決定・6枠パッキング）と `required_fills` の本体は**穴のまま**。
> 「手がかりを足す」形の採用はよいが、「答えを書く」形は退ける。
>
> **実装確認で判明した事実（採否の根拠に使用）**:
> - `Condition`/`Broken`/`Kind`/`Item` は src で全て `#[derive(Debug, PartialEq)]` 付き。
>   → `required_fills` の `c == g` は実際に通る（第0章の型塊が derive を省いているのが不整合の元）。
> - `Kind` だけ `pub` が無いのは src の忠実な再現（書き忘れではない）。
> - `Broken.condition`/`missing`・`Kind` は private フィールド（ソルバから読むには可視性の設計が要る）。

## 2. 教師への具体的改訂指示

各指示に**開示線**（ここまで骨格／ここから穴）を明記した。線を越えて穴を埋めないこと。

### A. 中核型の骨格を足す（#16, #19, #30 ― Top1）

- **第1章1.4 に `Snapshot` の struct を1つ**。設計仕様 §5 の3要素に厳密に揃える:
  ```
  部屋の有向グラフ / 各部屋の GroundStack / item→(部屋, 段) 索引
  ```
  **開示線**: フィールド名と型の形（例 `rooms: HashMap<RoomId, GroundStack>`、`index: HashMap<Variant, ...>`、
  グラフの辺表現）**まで**。索引の値を単一 `(RoomId, usize)` にするか `Vec` にするかは §1.4 の既存コラム（重複問題）
  が未確定と述べているので、**骨格では単純形を置き、確定はコラムに残す**。メソッド本体・巡回・掘りロジックは穴。
- **第4章4.4 の直前に `State` の struct**。設計仕様 §6 に揃え `{ inventory: Vec<Item>, current_room: RoomId }`
  程度の最小形。**開示線**: フィールドのみ。`State::empty_at` 等の実装は書かない（第5章のヘルパ #33 と整合）。
- `RoomId` は「部屋の識別子（後で定義）」の一言（#19）。`usize` の由来説明は不要。

### B. 全体の骨組みを図/擬似コードで1枚（#27, #38 ― Top2）

- **第3章（3.3 の後 or 章末）に、部品の呼び出し/データフローを1枚**。最低限:
  ```
  solve(&Variant) ─(索引で Variant→Item)→ plan(&Item, goal=Pristine)
    plan ─→ required_fills(&Condition, &Condition) -> Vec<Fill>   … 分解（第2・3章）
         ─→ Fill を Step 列へ … ここでスケジューラ（第4章）
  ```
  併せて生徒が詰まった2点を図中で解消: **(a) `Variant→Item` を索引で引く**こと、**(b) `Fill`→`Step` の変換が
  どこで起きるか**、**(c) `plan` と `solve` の役割差**（`plan`=1 item を Step 列に、`solve`=入口＋層2＋不可能判定）。
  **開示線**: 「誰が誰を呼び、データがどう流れるか」の骨格まで。**層2の中身（順序決定・6枠パッキング）は
  図の中でも「スケジューラ＝穴」の箱に留め、アルゴリズムは描かない**。
- **第2章 or 第3章に keypad の依存木図**を1つ。設計仕様 §8 に既に ASCII 依存木がある（`keypad→…→radio〈欠 antenna で止まる〉`）ので
  それを教材化。**radio が antenna 欠品で止まる様子が一目で分かる図**は罠の理解に直結し、開示safe（「何が要るか」であって
  スケジュールではない）。
- **枠ピーク推移図は却下**。keypad の具体的な手順列に沿ったピーク推移を描くと、それは層2の解（有効な並び）を
  提示することになり開示線を越える。**描くなら増減規則の抽象図（`take`+1 / `combine`−1 / `incinerate`−1 / `go`±0）まで**。

### C. Rust 低レイヤ土台の再配置＋用語衝突（#2, #9, #11, #22, #28, #29, #20, #37 ― Top3）

- **第1章の冒頭に短い「3点セット導入」**（#2, #10, #24）。所有権（値に所有者は1つ、所有者が消えると値も drop）・
  借用（読むだけなら所有権を取らない）・move（値渡しで所有権が移り、元は使えなくなる）を**数段落**。
  **開示線**: 既知概念（enum/match/再帰/TDD）は再説明しない。**新規は「値には所有者」「借用」「move」「スタック/ヒープ」「drop」だけ**。
  詳細は各章で回収（借用→第2章、move/drop→第4章）の現構成を保ち、頭に要旨だけ前倒しする。
- **1.1 にスタック/ヒープの2文**（#9）: 「Rust は既定で値をスタックに置くのでコンパイル時にサイズが要る。`Box` は
  ヒープへ逃がしサイズをポインタ1本に固定する」程度。`recursive type has infinite size` の説明の**手前**に置く。
- **`drop` の用語衝突を解消（最優先, #29）**:
  - 4.1（Rust の drop）に「値はスコープを抜けると drop＝破棄される」の1文定義を足す。
  - 4.3 のゲーム操作は「**（ゲームの）`drop` コマンド**」と明記して Rust の drop と区別。可能なら地の文では
    ゲーム側を「床へ戻す操作」等と開いて同語衝突を避ける（改名の具体は教師裁量）。
- **1.2 に「`derive` はトレイト実装の自動生成」の一言**（#11）。`Hash`/`Eq` の用途は既述なので、`Clone`/`Debug` を
  並べた理由（複製する・`assert_eq!` で表示する）を一言添える。
- **第2章に match ergonomics の一言**（#22）: 「借用（`&Condition`）を `match` で分解すると、束縛（`now`）は自動で参照になる」。
- **3.3 に `&*now.condition` の一言**（#28）: 「`*` で `Box` の中身を取り出し、`&` で借用し直す」。
- **生英語を日本語に開く**: 1.5 の `newtype`（#20）＝「1フィールドのタプル構造体で別の型を作るやり方」、
  終章の `frontier`（#37）＝「探索の未展開集合」。

### D. 未定義語のその場定義（#3, #4, #5, #7, #8, #12, #31）

- `UM`（#3）: 「手順を実行する対象。シェルの先にいる本体」程度。正体不明の三文字を残さない。
- 「6枠」（#4）: 「インベントリは6枠（ゲーム規則）」。
- 「在庫ゴミ」（#5）: 「地面の山に紛れる不要品」。
- `Broken(Broken)`（#7）: 「バリアント名 `Broken` と型 `Broken` は別物」。
- `Kind` の `pub` 無し（#8）: 「src の通り（`Kind` は非公開）」。**書き忘れではない**と確認済み。

### E. 整合・重複・穴マクロ（#6, #15, #17, #18, #21, #23, #26, #33, #35）

- **第0章の型塊に `#[derive(Debug, PartialEq)]` を付す（#21）**。src と一致し、`required_fills` の `c == g` が
  通る根拠が読者に見える。**開示safe（属性はアルゴリズムではない）**。第2章側の「PartialEq が要る」疑問がここで解ける。
  併せて `now.missing`/`now.condition` は src では private フィールドである旨、**NOTE で1行触れてよい**
  （「ソルバから読むには可視性の設計が要る＝読者の課題」。ここは**答えを書かず手がかりに留める**）。
- `take_top` の不整合解消（#18）: サンプルを推奨（末尾=上・`pop`）に合わせるか、「サンプルは説明用、実装は末尾=上を勧める」と明記。
  段番号の向きは A の `Snapshot` 骨格が決まれば自然に定まる。
- `unimplemented!()`→`todo!()` に統一（#23）。
- `Kind` 再掲（#15）: 「第0章の再掲」と断るか、差分（`adjective` が無い点）だけ見せる。
- parser 平坦化の橋渡し1文（#17）／`simulate_peak_holding` が `Sim` を回す1文（#35）。**開示線**: いずれも1文の橋渡しのみ。
  変換器・シミュレータの本体は読者が書く（穴）。
- 宙吊りリンクに「下に再掲」注記（#6）、`Box::new(Pristine)` に「（概念的に）」注記 or `Condition::Pristine` へ揃える（#26）。
- テスト用ヘルパ一覧（#33）: `load_snapshot`/`variant`/`State::empty_at` を短く列挙し各々の返り値を一言。`.expect` に
  「`Ok` を取り出す、失敗ならメッセージ付きで落ちる」の一言。**開示線**: シグネチャ/返り値まで。`load_snapshot`（parse 橋渡し）の実装は書かない。

### F. コラムの交通整理と §N 要約（#39, #1, #13）

- **各【未確定】コラムに統一ラベル**（#39）: 「tutorial では踏まない（Chicago で効く）」/「tutorial で踏む（今決める）」。
  約10個あるので、着手時にどれを埋めるか迷わせない。開示に無関係で高価値。
- `§N` 参照の**抜けている要約だけ**1〜2文補う（#1）。大半は既に要約付きなので全面追記はしない。冒頭に「本書だけで
  核心3点は実装できる／Chicago 以降は原典が要る」の自己完結宣言を1文（巻末「参考」の不安を先に解く）。
- enum 構造体バリアント記法に軽い注（#13、低優先）。

### G. 探索状態の型の器のみ（#32 ― 開示線に注意）

- 4.4 の探索コラムで、状態「(手持ち集合, 各山の掘り深さ, 未達成スロット)」を**Rust の器で持つならどの型か**を半歩だけ
  （例: 手持ち集合＝`HashSet<Variant>`、掘り深さ＝山ごとの `usize`）。
  **開示線（厳守）**: **器（コレクション型）の naming まで**。**遷移関数・枝刈り・探索の駆動（次の1手の選び方）は書かない**。
  生徒自身「模範的な穴」と評しており手がかり不足ではないので、これは低優先の親切に留める。踏み越えそうなら**却下でよい**。

## 3. 日本語修正指示

初稿は**元から日本語で書かれており、英語直訳臭・係り受けの破綻はほぼ無い**（後述の美点）。拾えたのは局所のみ。

- **生英語の混入**（散文中。コード識別子・コマンド名は除外）:
  - `newtype`（1.5 本文・コメント）→「1フィールドのタプル構造体で別の型を作るやり方」等に開く（#20）。
  - `frontier`（終章「DFS/BFS、frontier・訪問済み判定」）→「探索の未展開集合（frontier）」（#37）。
  - `fixture`（第0章・第3章・第5章で反復）→ 低優先。established 語だが、開くなら「フィクスチャ」or「検証用データ」。
  - `move`（第4章）→ 技術用語として許容だが表記を統一（「move」か「ムーブ」か）。定義自体は本文にあり問題なし。
- **語選択**:
  - 5.3「手順列を `enum` の `Vec` にしておいた**配当**がここで効きます」―「配当」は不自然（dividend の直訳臭）。「利点」「恩恵」へ。
  - 「効く/効いている」の反復（5.3「配当が…効きます」、3.3「罠が効く形」ほか）。負の含意がない箇所は「活きる」「役立つ」等に散らし、多用を避ける。
- **一文が長い/係り受け**:
  - 5.4（在庫ゴミの緩いテスト）「当面は『radio や keypad を掘り出すために…最後まで持ち越されていない』くらいの緩い性質で受け、
    処分方針が固まってから締めるのが無難です。」― 括弧の入れ子で一文が長い。2文に分割を推奨。
