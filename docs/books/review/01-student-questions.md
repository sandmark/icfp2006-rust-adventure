## 第0章 この本が扱う範囲

- **場所**: 「設計仕様のソルバは 3 コマンド（`walk` / `solve` / `make`）から成りますが」「`make`（手順を UM へ流す）」
  **軸**: What（未定義語）
  **引っかかり**: **`UM` が最後まで定義されない**（ここと終章 §make に登場）。低レイヤ未経験の私には UM が何の略で、
  何をする相手なのか分からない。`make` が「手順を UM へ流す」と言われても、UM の像が結べない。
  **希望**: 初出で一言「UM（手順を実行する対象。シェルの先にいる本体）」程度の説明がほしい。ネタバレを避けたいなら
  抽象的な一文でよいので、正体不明の三文字だけが残らないようにしてほしい。

- **場所**: 「同時に抱える枠数の最大を 6 以下に収める」「6 枠制約」
  **軸**: Why
  **引っかかり**: 「6」という数字が天下りで出てくる。なぜ 6 なのか（ゲーム規則なのか、設計上の都合なのか）が
  ここでは分からない。第4章まで読むとインベントリ枠のことだと分かるが、初出時点では宙に浮く。
  **希望**: 初出に「インベントリは 6 枠（ゲーム規則）」の一言を添える。

- **場所**: 「LIFO 掘り＋6枠制約＋**在庫ゴミ**の `incinerate`」
  **軸**: What（造語）
  **引っかかり**: 「在庫ゴミ」という語がやや独自。第4.3章を読むと「山を掘る過程で邪魔になる不要品」と分かるが、
  「在庫」は普通インベントリ（手持ち）を連想させるので、地面の山のゴミなのか手持ちのゴミなのか初見で迷う。
  **希望**: 「地面の山に紛れる不要品」など、初出で指すものを明確に。

- **場所**: 「シェル本体の `parser.rs` が、VM の XML 応答を Rust の型に変換済みです（`CLAUDE.md` 参照）」
  **軸**: 自己完結
  **引っかかり**: `CLAUDE.md` 参照・`parser.rs` 参照が出る。ただし直後に4つの型をインラインで見せてくれるので、
  ここは実質困らない（良い配慮）。とはいえ「（`CLAUDE.md` 参照）」は私には辿れない宙吊りリンク。
  **希望**: 参照は残してよいが、「本書だけで読めるよう下に再掲する」と明示。

- **場所**: 4つの型のコードブロック（`Condition` / `Broken` / `Kind` / `Item`）
  **軸**: コード / What
  **引っかかり**: これは良いブロックで、コメントも親切。ただし低レイヤ初学者として細かく詰まる:
  - `enum Condition { Pristine, Broken(Broken) }` の `Broken(Broken)` は「バリアント名 `Broken` が、型 `Broken` の値を持つ」
    という形。同名が重なるので初見で「これは何を包んでいるのか」を一瞬読み違える。
  - `Kind` だけ `pub` が無い（他3つは `pub`）。意図的な差なのか書き忘れなのか分からず気になる。
  **希望**: `Broken(Broken)` に「バリアント名と型名が同名（別物）」の一言。`pub` の有無に意味があるなら触れる、
  無ければ揃える。

- **場所**: 「fixture は `local/tutorial.xml`。…`keypad` を `pristine` にするのがゴールです」
  **軸**: What（良い点）
  **引っかかり**: ここは具体的でありがたい。2部屋名・ゴールが明示されていて像が結べる。指摘なし（良かった点として記録）。

## 第1章 ドメインを Rust の型で表す

### 1.1 状態は enum ― 再帰には `Box`

- **場所**: 「コンパイラは『この値ひとつの大きさ（バイト数）』を確定できず、`recursive type has infinite size` で止まります」
  **軸**: Why（低レイヤ前提）
  **引っかかり**: 説明の方向は良い。ただし私のような GC 言語出身者には、そもそも **「なぜコンパイラが値の大きさを
  静的に知らないといけないのか」** が腑に落ちない。Ruby/Clojure では値の大きさなど気にしたことがない。「ヒープ」「ポインタ」
  「スタック」という語が前提として使われるが、この本の読者設定（低レイヤ未経験）だと、この3語こそ最初の壁になりうる。
  「サイズが決まっている＝ポインタ1本」までは分かるが、その手前の「値はどこかに置かれ、置き場所によってサイズ制約が違う」
  が省かれている。
  **希望**: 「Rust は既定で値をスタックに置き、そのためコンパイル時にサイズが要る。`Box` はヒープへ逃がしてサイズを
  ポインタ1本に固定する」程度の、スタック/ヒープの2文導入がほしい。ここが本書で最初に低レイヤ知識を要求する箇所なので、
  ここを厚くすると後が楽。

- **場所**: 【コラム】`Rc`/`Arc` ではなく `Box` でよいか ―「`Box`（唯一の所有者）」「1 つの所有者がまるごと持つ」
  **軸**: Why（横断・導入順）
  **引っかかり**: ここで初めて **「所有者」「所有」** という語が実質デビューするが、所有権の定義はまだ与えられていない
  （借用は第2章、move は第4章）。予告（冒頭）では目玉のはずの所有権が、定義前にコラムの中で当然のように使われ始める。
  `Rc`/`Arc` という新しい型名も出るが「本書では要らない」で流れる。初学者としては「唯一の所有者」の"唯一"が効くのか、
  まだ実感がない。
  **希望**: 所有権の最小限の定義（値には所有者が1つ、所有者が消えると値も drop）を、このコラムより前に置く。
  そうすれば「`Box`＝唯一の所有者」が意味を持って読める。

### 1.2 アイテムの同一性 ― `Variant`

- **場所**: `#[derive(Clone, PartialEq, Eq, Hash, Debug)]`
  **軸**: What / コード（初出構文）
  **引っかかり**: `#[derive(...)]` が初登場。効能（`HashMap` のキーに使える／`Hash` と `Eq` が揃うのが条件）は
  説明があり、そこは助かる。ただし **「これら（`Clone`/`PartialEq`/`Eq`/`Hash`/`Debug`）はトレイトで、`derive` は実装を
  自動生成する」という一段が無い**。本書は「trait」という語をここまで一度も使っていないので、`derive` が何を"導出"して
  いるのかがぼんやりする。また `Hash`/`Eq` の用途は書かれるが、`Clone`/`Debug` を何のために付けたのかは触れられない
  （後でテストや複製に効くのだろうと推測するだけ）。
  **希望**: 「`derive` はトレイト実装の自動生成」を一言。`Clone`/`Debug` を並べた理由（複製する・`assert_eq!` で表示する等）も
  一言添える。

- **場所**: 【コラム／未確定】adjective 無しの同一性 ―「Chicago で `name` が衝突するバリアント群（`X-1623-GTO` は 9 種など）」
  **軸**: What（未定義語）
  **引っかかり**: **`Chicago` がここで初出、以降ずっと定義なしで多用される**（1.4・3.3・終章など）。tutorial との対比で
  「より大きく難しい実データ」らしい、とは推測できるが、Chicago が何なのか本文からは分からない。私は「後で出てくる大きな
  ステージらしい」と当たりを付けて読み進めたが、確信は持てない。
  **希望**: 初出で「Chicago（tutorial より大きい実データ。`local/chicago-rooms.xml`）」程度の定義を1回。ネタバレを避けたいなら
  「本書の射程外の、より大規模なデータ」でよい。

- **場所**: A案 `Option<String>` / B案 `enum Identity { Named(String), Variant{ name, adjective } }`
  **軸**: How（良い穴）
  **引っかかり**: 未確定を2案で並べるのは分かりやすい。実データで確定、という道筋も見える。良い穴として尊重。指摘は軽微:
  B案の `Variant{ name, adjective }` は enum の構造体バリアント記法だが、これも初学者には初見の構文。
  **希望**: 特になし（穴として妥当）。強いて言えば構造体バリアント記法に一言。

### 1.3 スロットは「名前＋目標状態」

- **場所**: 「『フィールドが無い』ことが仕様の主張になっているのは気持ちのいい設計です」
  **軸**: 冗長（軽微）
  **引っかかり**: 設計の良し悪しへの感想。私には既知の感覚（型で語らせる）なので、無くても困らない。害はない程度。
  **希望**: 残してよいが、この種の"気持ちのいい"評は絞ってよい。

- **場所**: `struct Kind { name, condition, // adjective は無い ... }`
  **軸**: 冗長（軽微・重複）
  **引っかかり**: `Kind` は第0章（型の再掲）で既に一度出ている。ここで再掲されるのは強調の意図と分かるが、
  ほぼ同じ定義が2回。
  **希望**: 「第0章の `Kind` を再掲」と断るか、差分（`adjective` が無い点）だけを見せる。

### 1.4 地面の LIFO ― `Vec` へ持ち替え

- **場所**: 「**Snapshot** 側では山を `Vec` に持ち替えます」
  **軸**: 自己完結 / What（**重大**）
  **引っかかり**: **`Snapshot` がここで初出、以降ソルバの中心的な引数になるのに、`struct Snapshot { ... }` の定義が
  最後まで一度も出ない**。solve のシグネチャ（第4章）、テスト（第5章 `load_snapshot`）、索引コラム（本節）で
  当然のように使われるが、Snapshot が何を束ねる型なのか（GroundStack の集まり？ 索引？ 部屋グラフ？）が本文から
  組み立てられない。実装しようとすると、まずここで手が止まる。「これは元資料を見ないと分からない」と感じた最大の箇所。
  **希望**: `Snapshot` の最小の struct 定義（各部屋の `GroundStack`、item 索引、部屋グラフ等、本書の射程で必要な
  フィールドだけ）を1つ示してほしい。穴でよいが、フィールドの骨格が無いと solve のシグネチャが宙に浮く。

- **場所**: 「パーサ側にも `piled_on` を平らな `Vec<Item>` に均す処理があります」
  **軸**: 自己完結
  **引っかかり**: parser 側に平坦化処理がある、と言われるが実体は見えない。`GroundStack.items: Vec<Item>` を
  どうやって parser 出力から得るのか（自分で均すのか、既にあるのか）が曖昧。
  **希望**: 「parser の出力を `GroundStack` に詰める橋渡し」を1スニペットか1文で明示。

- **場所**: `take_top` のサンプル（`remove(0)`）と、直後の本文「上 = 末尾に採れば `push`/`pop` だけで LIFO が完結」
  **軸**: How（自己矛盾ぎみ）
  **引っかかり**: サンプルコードは `remove(0)`（index 0＝上、O(n)）で書かれているのに、本文は「上＝末尾で `pop`（O(1)）が
  素直」と勧める。読者としては「結局どっちで実装すればいいのか」で迷う。NOTE で「索引の段番号の向きと揃えろ」と言われるが、
  その索引自体が未定義（次のコラム）なので、揃える相手が無く決めきれない。
  **希望**: サンプルを推奨（末尾＝上、`pop`）に合わせるか、「サンプルは説明用、実装は末尾＝上を勧める」と明記。段番号の
  向きは、索引の骨格（上の Snapshot の件）が示されれば自然に決まる。

- **場所**: 【コラム／未確定】item 索引 ―「`HashMap<Variant, (RoomId, usize)>`」
  **軸**: What（未定義語・軽微）
  **引っかかり**: `RoomId` が未定義（何で部屋を識別するのか）。`usize` も、なぜ普通の整数でなく `usize` なのかは
  低レイヤ初学者には引っかかる（説明は無くても実害は小さい）。
  **希望**: `RoomId` を「部屋の識別子（後で定義）」と一言。`usize` は流してよい。

### 1.5 手順列は `Step` の `Vec`

- **場所**: `enum Step { Take(Variant), Combine { target, part }, Incinerate(Variant), Go(Direction) }`
  **軸**: コード（良い点）
  **引っかかり**: タプルバリアントと構造体バリアントが混在する良い実例で、各行コメントも親切。ここは分かりやすい。
  **希望**: 特になし。

- **場所**: `struct Direction(String); // newtype に包んでおくと取り違えにくい`
  **軸**: 日本語 / What（軽微）
  **引っかかり**: 「newtype」が生の英語のまま。パターンの効能（取り違え防止）は書かれているので意味は取れるが、
  低レイヤ初学者には「newtype」という単語自体が新出。
  **希望**: 「newtype（1フィールドだけのタプル構造体で別の型を作るやり方）」と初出で一言、または「新型ラッパ」等に開く。

## 第2章 再帰的な依存分解

- **場所**: `required_fills` のスケルトン `match (current, goal) { (c, g) if c == g => Vec::new(), ... }`
  **軸**: How / コード（**要確認**）
  **引っかかり**: `c == g` で `Condition` 同士を比較しているが、第0章で示された `Condition`/`Broken` には
  `#[derive(PartialEq)]` が付いていない。`==` が使えるには `PartialEq` が要るはず。既存 parser 型に既に `==` があるのか、
  自分で derive を足すのかが本文から分からない。実装で最初にコンパイルを通すとき、ここで詰まりそう。
  **希望**: 「`Condition` に `PartialEq`/`Eq` を derive しておく（既存に無ければ足す）」を明記。第0章の型定義にも derive を
  見せておくと一貫する。

- **場所**: `(Condition::Broken(now), goal) => { ... }`（`&Condition` を分解して `now` を束縛）
  **軸**: How / コード（低レイヤ非自明）
  **引っかかり**: `required_fills` は `current: &Condition`（借用）を受けるのに、`match` で `Condition::Broken(now)` と
  書くと `now` が自動的に参照（`&Broken`）になる。私の既知言語には無い挙動（match ergonomics / 既定束縛モード）で、
  「`&` や `ref` を書かなくていいのか？」と身構える。本文に説明が無い。
  **希望**: 「借用を `match` で分解すると束縛は自動で参照になる」を一言。ここは Rust 初学者がよく転ぶ所なので、
  短くても触れる価値がある。

- **場所**: `unimplemented!()`（260行あたり）と `todo!(...)`（270行あたり）が同じ「穴」に混在
  **軸**: What（軽微）
  **引っかかり**: 「穴」を示すマクロが2種類。違いの説明が無いので、使い分けの意図があるのか（無いのか）分からない。
  **希望**: どちらかに統一するか、「本書では穴＝`todo!()`」と決めて統一。

- **場所**: 借用の説明「`&Condition` の借用で受けているのは…読むだけだから。所有権を取らないので、同じ `Condition` を
  何度でも読めます」
  **軸**: Why（横断・導入順／良い点）
  **引っかかり**: 借用の説明として分かりやすい。ただしこれが**借用の初回のまともな導入**で、第1章のコラムでは
  「所有」を定義前に使っていた。順序として、借用の説明が2章まで来ないのが遅い。
  **希望**: 内容は良いので、第1章冒頭の「3点セット導入」にこの説明の要旨を前倒しできると全体が滑らかになる。

- **場所**: 【穴】`required_fills` の本体
  **軸**: How（良い穴）
  **引っかかり**: 「第3章で埋め方を見せる」と明言され、道筋が見える。良い穴として尊重。指摘なし。

- **場所**: 【コラム／未確定】木の底 ―「作業ノート『依存の再帰には底がある』」参照
  **軸**: 自己完結（軽微）
  **引っかかり**: 「作業ノート」という私の持たない資料への参照。ただし主張（底がある＝仮説、循環したら止まらない、
  保険に訪問集合）は本文で完結しているので実害は小さい。
  **希望**: 参照は残してよい。主張が本文で閉じているので現状で十分。

## 第3章 スロット条件で止まる罠（心臓部）

- **場所**: 3.1 radio の XML 抜粋 ＋「差 `{transistor, antenna} − {antenna} = {transistor}`」
  **軸**: How（本書の白眉・良い点）
  **引っかかり**: ここは本当に分かりやすい。XML 実物→型→「差を取る」まで具体で降りてくれるので、`required_fills` の
  穴に何を書くかが手に取るように分かる。第2章の穴の埋め方がここで回収される構成も良い。指摘は良かった点として記録。
  **希望**: なし（むしろこの具体度を他章にも欲しい）。

- **場所**: 「（fixture 313–337 行）」「（fixture 157–184 行）」
  **軸**: 自己完結（軽微）
  **引っかかり**: `tutorial.xml` の行番号への参照。私は原本を持たないので行番号は照合できない。ただし該当 XML の抜粋が
  本文にあるので、理解は困らない。
  **希望**: 行番号は残してよいが、抜粋があるので必須ではない。抜粋がある限り問題なし。

- **場所**: 「`goal` が…`Condition::Broken(Broken{ condition: Box::new(Pristine), missing: [antenna] })` になります」
  **軸**: コード（軽微・整合）
  **引っかかり**: `Box::new(Pristine)` と `Pristine` を裸で書いているが、他所では `Condition::Pristine` とフルパス。
  `missing: [antenna]` も本来 `Vec<Kind>` で、`[antenna]` は配列リテラル風の略記（`antenna` も本来 `Kind`）。
  地の文の擬似コードと分かるが、初学者は「これはそのままコンパイルできる形？」と一瞬迷う。
  **希望**: 擬似コードだと分かるよう「（概念的に）」と断るか、`Condition::Pristine` に揃える。

- **場所**: 3.2 `plan` / 3.3 と、第2章 `required_fills`、第4章 `solve`、4.1 `combine`
  **軸**: How（**重大・全体構造**）
  **引っかかり**: 実装のために必要なのに欠けている最大の"つなぎ"。本書には4つの関数シグネチャが出る:
  - `required_fills(current: &Condition, goal: &Condition) -> Vec<Fill>`
  - `plan(item: &Item, goal: &Condition) -> Vec<Step>`
  - `solve(item: &Variant, snapshot: &Snapshot, state: &State) -> Result<Vec<Step>, Unsolvable>`
  - `combine(a: &mut Item, b: Item)`
  これらが**どう呼び合うのか**が本文から組み立てられない。`solve` は `&Variant` を受けるが `plan` は `&Item` を受ける。
  Variant → Item をどこで（Snapshot の索引で？）引くのか。`required_fills` が返す `Fill`（`slot: Kind` だけ持つ）が、
  どうやって `Step`（`Take`/`Combine`…）の列に化けるのか。`plan` と `solve` は役割が重なって見えるが別物なのか。
  各部品の説明は丁寧なのに、**全体の呼び出し構造（誰が誰を呼び、データがどう流れるか）を1枚に描いた図や擬似コードが無い**。
  **希望**: 「`solve` → `required_fills`（分解）→ `Fill` を `Step` 列へ → スケジューラ」という**全体の骨組みを1つの図か
  擬似コード**で示してほしい。`Fill` から `Step` への変換がどこで起きるかを明記。これが無いと、部品は分かっても
  組み上げられない。

- **場所**: 3.3「`&*now.condition` のように…借用でたどる」
  **軸**: コード（低レイヤ非自明）
  **引っかかり**: `&*` が説明なしで出る。`*` で `Box` の中身へ、`&` で再び借用、という2段操作は初学者には暗号。
  **希望**: 「`*` で `Box` の中身を取り出し、`&` で借用し直す」の一言。

## 第4章 LIFO 掘りと 6 枠のスケジューリング

- **場所**: 4.1 `combine(a: &mut Item, b: Item)` ―「b は値で受け取る = move…消費されて使えない」「`b` は…終わりで **drop** される」
  **軸**: What / Why（低レイヤ・**用語衝突**）
  **引っかかり**: move の説明は非常に良い（シグネチャに語らせる、という締めも効いている）。ただし:
  - **`drop`（スコープ終端で値が破棄される）が初学者に新概念**。GC 言語ばかり触ってきた私には「関数の終わりで drop される」の
    "drop"（RAII・スコープを抜けると破棄）が当然ではない。move の説明とセットで、`drop` の1文定義が欲しい。
  - さらに深刻な**用語衝突**: ここの `drop` は Rust の「値の破棄」。ところが 4.3 では「`drop`（可否不明・依存しない）」＝
    **ゲームの"床に捨てる"コマンド**として同じ「drop」が出る。隣接セクションで同じ語が別義になり、確実に混乱する。
  **希望**: (1) move の説明に「値はスコープを抜けると drop（破棄）される」を1文。(2) 4.3 のゲーム操作の方は
  「（ゲームの）`drop` コマンド」と明記し、Rust の drop と区別する。用語をどちらか改名するのが一番安全。

- **場所**: 4.2 `struct Sim { inventory: Vec<Item>, ... }` / `over_capacity`
  **軸**: コード（良い点）
  **引っかかり**: 枠＝`Vec`、増減（take +1 / combine −1 / incinerate −1 / go ±0）の整理は明快。ここは良い。
  **希望**: なし。

- **場所**: 4.3【穴／未確定】処分3択 ―「`incinerate` してよいのは『木のどのスロットにも現れないバリアント』だけ、という不変条件」
  **軸**: How（良い穴）
  **引っかかり**: 未確定だが、埋めるための不変条件を具体的に与えてくれるので方向が見える。良い穴。
  **希望**: なし。ただし上記「drop 用語衝突」だけは要対応。

- **場所**: 4.4 `solve(item: &Variant, snapshot: &Snapshot, state: &State) -> Result<Vec<Step>, Unsolvable>`
  **軸**: 自己完結 / What（**重大**）
  **引っかかり**: `Snapshot` に続き **`State` も未定義**。テストの `State::empty_at("Junk Room")` から「手持ち＋現在地を持つ」
  らしいと逆算できるが、struct 定義は無い。`Result<T, E>` / `Ok` / `Err` は Rust の型で、Clojure/CL の either に近いと当たりは
  付くが、本書での初回導入としては素っ気ない（下の 486 行で理由は補足される）。
  **希望**: `State` の最小 struct（`inventory: Vec<Item>` と現在地）を示す。`Result`/`Ok`/`Err` に「成功は `Ok`、失敗は
  理由付きの `Err`」の一言。

- **場所**: 4.5 「`uploader` / `downloader` などをどの順で作り」
  **軸**: What（未定義語・軽微）
  **引っかかり**: 「ターゲット」「`uploader`/`downloader`」が例として出るが説明はない。層1の対象品らしい、で読み流せる程度。
  **希望**: 「ターゲット（最終的に作りたい item）」の一言があると層1/層2の対比が締まる。

- **場所**: 4.5「`state.inventory` に A を入れて `solve B` を呼び、`Err(OverCapacity)` が返るかで分かります」
  **軸**: Why（良い点）
  **引っかかり**: 層1（プレイヤー判断）を層2の実行で答える、という設計の腑への落ち方が具体的で良い。指摘なし。

- **場所**: 4.4/4.5【コラム／未確定】貪欲か探索か（擬似コード2種）
  **軸**: How（良い穴・本書最大の穴）
  **引っかかり**: 最大の穴に対して、貪欲・探索の擬似コードと「まず貪欲で通し、取りこぼしたら探索へ」という現実的な道筋を
  与えてくれる。「貪欲で最小ピーク」を事実として書かない姿勢も誠実。穴として十分に手がかりがある。
  **希望**: なし（模範的な穴の残し方）。強いて言えば、探索案の「状態 =（手持ち集合, 各山の掘り深さ, 未達成スロット）」を
  Rust の型でどう持つか（`HashSet` 等）を半歩だけ見せてもらえると着手が早い。

## 第5章 テストの書き方

- **場所**: 5.1 `load_snapshot("local/tutorial.xml")` / `State::empty_at("Junk Room")` / `variant("keypad")` / `.expect("solvable")`
  **軸**: How / 自己完結
  **引っかかり**: テストのために自分で書くべきヘルパが複数、暗黙に前提されている（`load_snapshot`・`State::empty_at`・
  `variant`）。これらは `Snapshot`/`State`/`Variant` の骨格が決まらないと書けないので、第1・4章の未定義（Snapshot/State）が
  ここで効いてくる。`.expect(...)`（`Result` を剥がし、失敗ならパニック）も初学者には新出だが説明なし。
  **希望**: 「テストに要るヘルパ一覧（`load_snapshot`/`variant`/`State::empty_at`）」を短く列挙し、それぞれが何を返すかを
  一言。`.expect` に「`Ok` を取り出す、失敗ならメッセージ付きで落ちる」の一言。

- **場所**: 5.1/5.2 `matches!(s, Step::Combine { target, part } if target.name == "radio" && part.name == "antenna")`
  **軸**: コード（良い点＋軽微）
  **引っかかり**: 「radio に antenna を挿す手順が**現れないこと**」を落とすテストは、第3章の罠と綺麗に対応していて良い。
  `matches!` とガードの組合せも実例として分かる。軽微な点として `target.name == "antenna"`（`String` と `&str` の比較）は
  Rust では通るが、初学者は「型が違うのに `==` していいのか」と一瞬迷うかも。
  **希望**: `matches!` に「パターン＋ガードに一致するか真偽で返すマクロ」の一言（既に近い説明あり）。`String == &str` は
  流してよい。

- **場所**: 5.3 `simulate_peak_holding(&steps, &snapshot)`
  **軸**: How
  **引っかかり**: ピーク保持数を数えるヘルパが要るが、これは実質 4.2 の `Sim` を使った小さなインタプリタを自分で書く作業。
  「take/combine/inc を数える」とはあるが、`go`（±0）や combine の −1 の扱いを含め、それなりの実装量。テストのつもりで
  読み始めると、ここで「もう一個ミニ実装が要るのか」と気づく。
  **希望**: `simulate_peak_holding` が中で `Sim` を回す、と一言つなぐ（4.2 との橋渡し）。骨格スニペットがあると尚良い。

- **場所**: 5.4 在庫ゴミ ＋【コラム／未確定】期待手順列の同値判定
  **軸**: How（良い点）
  **引っかかり**: 「処分3択が未確定だから緩いテストで受ける」「完全一致は実装の自由を縛るから性質検証で受ける」は
  TDD 実務として腑に落ちる。誠実で良い。指摘なし。
  **希望**: なし。

## 本全体として、実装に進めそうか ― 最大の障壁 Top 3

核心の考え方（再帰分解・スロット条件で止まる罠・LIFO/6枠）は、特に第3章が白眉で、**「何を作るか」は十分に伝わる**。
一方で **「部品をどう1つのプログラムに組み上げるか」の骨格が欠けており、いざ TDD で書き始めると詰まる**。障壁を3つ:

1. **中核型 `Snapshot` / `State` の定義が無い（自己完結の穴）**
   `solve` のシグネチャもテストのヘルパ（`load_snapshot`/`State::empty_at`）も、この2つが無いと書き出せない。
   「本書だけで読める」という約束と裏腹に、ここは元資料を見ないと埋まらない。フィールドの骨格だけでも本文に欲しい。

2. **関数どうしの呼び出し構造・データフローが描かれていない**
   `required_fills` / `plan` / `solve` / `combine` の各部品は丁寧なのに、誰が誰を呼び、`Fill` がどこで `Step` 列に変わるのかが
   本文から組み立てられない。全体を1枚に示す図か擬似コードが欲しい。

3. **Rust の低レイヤ土台（所有権・借用・move・drop・スタック/ヒープ）の導入が散在し、初出が定義に先行する**
   さらに `drop` が Rust の破棄とゲーム操作で同語別義。低レイヤ未経験の読者には、ここが各章で足を止める原因になる。
   第1章頭の短い導入＋用語衝突の解消で、大きく改善する。

> 逆に言えば、この3つ（型の骨格・全体構造の図・低レイヤ導入）が埋まれば、意図的な穴（`required_fills` 本体・層2
> スケジューラ・処分3択）は**手がかりが十分にある良い穴**なので、TDD で楽しみながら埋めていける手応えがあった。
