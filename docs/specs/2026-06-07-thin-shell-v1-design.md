## 1. 動機とねらい（ジャーナル）

`adventure` は剥き出しのベセスダゲーのようなもの——面白いが、補完も効かず、
依存関係の解決（dep hell）を人間が手作業でやるのはつらい。
そこで **薄いラッパー（modding）として「シェル」を自作し、攻略の足場にする** という方針を取る。

- シェルは UM を起動し、stdio でやりとりする
- ただしプレイヤーに見せるのは生の XML/sexp ではなく、整えた表示
- イメージは NetHack 的 UI だが、そこまではやらない。手始めは「本当に薄いシェル」
- 将来は `make keypad` のような自作高級コマンドで依存関係を分析・組み立てたい
- 余裕があれば TUI（インベントリ常時表示など）も

### このプロジェクトの根本目的
**実装ではなく学習・問題解決の楽しさが最優先。**
ユーザーは ICFP2006 を通して Rust を学習中であり、過去に挫折した経験がある。
よってコードは AI が書かず、**失敗するテストを足場に、ユーザー自身が書いて緑にしていく**
コーチング形式で進める。AI はハシゴを支える役。

### v1 で勉強したい題材（ユーザーが歓迎している部分）
- 外部プロセスとの stdio 通信（`std::process`）
- パイプとバイトストリームの所有権
- スレッドと並行 I/O
- バッファリング
- データ構造の設計（v1 では最小限）

## 2. v1 スコープ

一言で: `./local/um` を子プロセスとして起動し、自分（端末）と UM の間に
パイプで割り込み、両方向のバイトを std スレッド 2 本で**そのまま**中継する。
**「真ん中に座る」骨格を作り、UM と素通しで会話できる**のが完成条件。

### やる
- プロセス起動
- 双方向の透過中継
- UM 終了 / EOF で自分も終わる

### やらない（後のサブプロジェクト）
- 出力パース（XML / sexp）
- ロギング
- 高級コマンド（`make keypad` 等）
- TUI / raw モード

---

## 3. アーキテクチャ

### コンポーネント
| 部品 | 役割 | 依存 |
|---|---|---|
| 設定 | um のパス（既定 `./local/um`、上書き可）。既存の clap を流用 | clap |
| 起動 | `std::process::Command` で stdin/stdout を `piped()`、stderr は継承 | std |
| 中継 | 「自分の stdin→子の stdin」を別スレッド、「子の stdout→自分の stdout」をメイン。各方向 `io::copy` 一発 | std::thread, std::io |

### なぜ 2 スレッドなのか（最小である根拠）
`read()` はデータが来るまでブロックする。1 スレッドで入力・出力の両方を
読もうとすると、片方の待ちがもう片方を凍らせる。よって「独立に待てる流れ」を
2 本に分ける。内訳は「メインスレッド 1 本 ＋ 追加スレッド 1 本」で、
ブロッキング I/O で双方向を捌く限りこれが最小（async/ポーリングに逃げない前提）。

### データフロー
```
あなたの入力 → [スレッド: io::copy] → UM の stdin
UM の出力     → [メイン: io::copy] → あなたの画面
```

---

## 4. エラー / 際どい所（v1 で意識する点）
- **um が見つからない** → 分かりやすいエラーで終了
- **EOF の伝播**: Ctrl-D → 子 stdin を閉じる → UM 終了 → メインの copy が返って終了
- **既知のシコリ**: UM が先に死ぬと、stdin→子 のスレッドがキー入力待ちで
  ブロックしたまま残りうる。v1 では「プロセスごと終了で OS に任せる」で割り切る
  （後で綺麗にする余地として記録）

---

## 5. テストの縫い目
中継ロジックを「子プロセス起動」から切り離し、`Read` / `Write` を受け取る
純粋な関数に切り出す。こうすると **um を起動せずにメモリ上のバイト列で
中継をテストできる**。これが TDD の最初の「赤いテスト」になり、
コーチングの足場になる。
